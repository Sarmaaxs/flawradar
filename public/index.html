Check a website's security settings

Type an address. Wsec loads the home page the way a browser does, then looks at the certificate, response headers, cookies, DNS records and a few well-known files. You get a list of what to change, with configuration you can paste into nginx, Apache or Express.

New scan

Only public sites can be scanned. Addresses that point at private or internal networks are refused. Each scan starts at the home page of the host you enter.

What it looks at

Transport
HTTPS availability, the redirect from HTTP, certificate validity and key size, and whether TLS 1.0 and 1.1 are still accepted.
Headers
HSTS, Content-Security-Policy, X-Content-Type-Options, clickjacking protection, Referrer-Policy, Permissions-Policy, CORS, and version numbers in the Server header.
Cookies
Secure, HttpOnly and SameSite flags.
Content
Mixed content, scripts loaded from other sites without integrity hashes, and password forms.
DNS and mail
SPF, DMARC, CAA, and a security.txt file.
Exposure (deep scan)
Exposed Git directories, environment files, backups, debug pages, directory listings, and risky HTTP methods.

If your firewall blocks the scan

Bot filters and web application firewalls often block scanners they have not seen before. When that happens Wsec says so instead of grading the firewall's error page. Add the scanner addresses to your allow list and run it again. The whitelist page has the addresses, the user agent string, and ready-made rules for nginx, ModSecurity, fail2ban, ufw and Cloudflare.

How a scan runs

  1. Wsec resolves the host name and refuses anything that points at a private network.
  2. It requests the home page over HTTPS, falling back to HTTP, and reads the headers and cookies.
  3. In parallel it opens a TLS connection, makes one request to port 80, reads DNS records and looks for /.well-known/security.txt.
  4. Each check is scored. Failures cost points by severity, and the report gives the fix for each one.
